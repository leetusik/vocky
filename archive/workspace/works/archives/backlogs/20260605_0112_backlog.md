# Backlog

## Status Model

- Phase: `planned`, `in_progress`, `in_review`, `blocked`, `done`
- Slice: `todo`, `in_progress`, `in_review`, `changes_requested`, `done`

## Usage Rules

- Every newly created phase starts with only `decompose phase` and `phase review`.
- Phase-level notes are allowed and encouraged; they do not count as slices.
- Do not pre-seed phase-specific middle slices in a newly created backlog.
- Add phase-specific middle slices only from the dedicated `decompose phase` slice.
- Keep `phase review` open until the phase passes review.
- If review fails, add dedicated fix slices and rerun review.
- Keep this file limited to actively scheduled phases and slices.
- This file schedules backlog-driven phases and slices only; unrelated standalone requests do not need phase, slice, or work-item entries.
- Move intentionally deferred work into `works/deferred.md` instead of leaving it in the active backlog.
- Link active work items from `works/current/`.
- If every documented phase is `done` and every documented slice is `done`, run `scripts/rotate_backlog.sh` before starting new backlog-scheduled work.
- `scripts/rotate_backlog.sh` archives the active `works/backlog.md` file to `works/archives/backlogs/<timestamp>_backlog.md` and replaces it from `works/templates/backlog.md`.
- If the next request is standalone, completed-backlog rotation is housekeeping only and does not create a phase or slice for that request.
- Use stable phase IDs such as `P1`.
- Use stable slice IDs such as `P1.DECOMP`, `P1.S1`, `P1.F1`, and `P1.REVIEW`.
- Prefix each slice with `[ ]` until it is done, then switch it to `[x]`.
- Treat the checkbox as a visual summary only. The `Status` field remains authoritative.

## Active Phases

### Phase P1: Client Feedback REST — Operator Comments and End-User Read

- Phase ID: `P1`
- Objective: Add a client-facing REST surface, built on the existing `feedback_events` store, that lets integrating products (server-to-server, e.g. Changple5) review feedback and add/list operator-authored comments, and lets an end user read their own feedback together with those operator comments, while preserving the single canonical feedback store, the async capture path, and the trusted server-to-server model.
- Status: done
- Review outcome: pass
- Notes: Driven by a direct user request to build the client-side REST surface for integrating products (first consumer Changple5, server-to-server). Image attachments are handled separately in phase `P2`; P1 must stay forward-compatible with attachments but must not depend on them. Operator comments: introduce operator-authored comments as a new first-class concept, separate from the existing user `comment` field (the end user's own comment captured at feedback time) — most likely a one-to-many comment store keyed by feedback id with author and timestamps; expose operator add and list through the existing Admin REST review track (`/admin/api/*`, the established human/operator surface) rather than a parallel operator API, and do not overload `comment` or the Admin PATCH editable set. End-user read: add a public REST read scoped strictly to a single `user_id` plus `source_product`, returning that user's feedback together with its operator comments; this deliberately expands the currently capture-only public REST surface, so `docs/product.md`, `docs/architecture.md`, and `docs/api.md` must consciously adopt it. Auth is trusted server-to-server: the integrating product authenticates its own user, then calls Vocky with that `user_id` and the API bearer token (`VOCKY_API_AUTH_TOKEN`); Vocky enforces `user_id` + `source_product` scoping and never returns cross-user data — there are no Vocky-native end-user accounts. Reuse existing infrastructure: bearer-token middleware (`src/vocky/auth.py`), the service-locator DI plus repository/service pattern (`src/vocky/feedback/`), Pydantic validation (`src/vocky/capture.py`), Alembic migrations, the `feedback_events` table with its existing `user_id`/`source_product` indexes and filters, `serialize_record`, and the pytest + httpx ASGITransport + fakeredis test pattern. Keep public Vocky generic — no Changple-specific concepts in code or public docs (`docs/changple5-apply.md` is a private, gitignored handoff; Changple is just the first consumer). Out of scope unless explicitly promoted: image attachments (phase `P2`), multi-tenant, Vocky-native end-user accounts, two-way comment threads or end-user replies (this phase is operator-to-user one-way visibility), analytics/classification, and the trajectory export concern (`D1`/`C1`). Doc triggers on completion: `docs/product.md` (public REST gains a scoped read), `docs/architecture.md` (operator-comment store and the new read surface), `docs/api.md` (operator-comment add/list and user-feedback-read contracts).

### Phase P2: Feedback Image Attachments

- Phase ID: `P2`
- Objective: Let end users attach images (jpg/jpeg/png and similar raster types) to feedback — e.g. screenshots — and surface those attachments in the operator-review and end-user-read responses from P1, introducing Vocky's first file-storage subsystem without breaking the async capture path.
- Status: done
- Review outcome: pass
- Notes: Builds on phase `P1` and depends on it: extends P1's operator-review and end-user-read responses to include attachment references. Vocky has no file storage today, so the `decompose phase` slice must choose a storage backend (a local filesystem volume is acceptable for the self-hosted single-tenant MVP; S3-compatible is optional), the upload flow, validation rules (allowed image MIME types such as jpg/jpeg/png/gif/webp, maximum file size, and maximum count per feedback), a new attachment store linked to `feedback_events`, and an authenticated download endpoint that reuses P1's per-user/operator access scoping (an end user sees only their own attachments; operators see all attachments for their product). Async-capture constraint: capture is asynchronous (`202 Accepted` then Redis queue then worker persists) and binaries do not belong in the JSON queue, so attachments most likely need a synchronous upload-and-store step that returns attachment ids which the capture payload references and the worker links on persist — flag this explicitly during decomposition. Reuse the same infrastructure as P1 (auth middleware, service/repository pattern, Alembic, tests) and add a storage abstraction plus an attachments table and migration. Keep public Vocky generic with no Changple-specific concepts. Out of scope unless explicitly promoted: non-image attachments (pdf/video/documents), image processing such as thumbnails or virus scanning, CDN delivery, and multi-tenant. Doc triggers on completion: `docs/product.md` (attachments introduced), `docs/architecture.md` (the file-storage subsystem and its link to the async capture path), `docs/api.md` (attachment upload/download contracts and attachment fields in read responses).
